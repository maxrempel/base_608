## DECISIONS MADE + WHY

1. **Identified the "image maker"** - it's the **imager** at `localhost:8779/imager`, a still-image browser. The filter logic lives in two places: `runner_core.js` (browser) and `combo_gui.py` (server).

2. **Confirmed the symptom is behavioral, not visual.** The filter bar renders correctly (Photo: all/active/approved/junk; Show: shots/plates/canons; text search; Stars 5-0). The pollution is intermittent - a flash of wrong images that then gets cleaned up by a recently added 2-second re-assertion timer.

3. **Traced the two data sources that feed the grid:**
   - **Shots** (`/api/jobs`) - server respects `arr=` scene parameter. Correctly scoped.
   - **Plates** (`/api/plates`) - server returns **all** `role='plate'` rows, with **no scene/arrangement filter at all**. It doesn't even read the `arr=` query parameter.

4. **Diagnosed the root cause** by examining live data in the browser:
   - Total in-memory rows: 1,457
   - Passing current scene filter: 298 (all correct, scene 11)
   - Hidden by filter: 1,159
   - Of those hidden: ~927 have an arrangement ID belonging to **other scenes** (mostly prehistoric "scene 2"), ~232 have **arrangement_id = NULL** (no scene at all)
   - **Exactly zero hidden rows are shots.** 100% of the pollution is plates.

5. **Why the other chat is stuck:** The D04B session recently added a fix that re-asserts the browser-side arrangement filter every 2 seconds. This successfully masks the problem - by the time a human looks, the filter has already cleaned up the grid. So every time someone checks, things look fine. But the wrong plates still **flash in momentarily** during load or after text-search clears, because the filter briefly resets before the timer fires.

6. **The actual fix needed:** Add server-side scene scoping to `/api/plates`, mirroring how `/api/jobs` already works. If the server only returns plates belonging to the selected scene's arrangements, there's nothing wrong to flash - no reliance on a 2-second browser bailout.

7. **No code was touched.** The hot files (`runner_core.js`, `combo_gui.py`) are being edited by other D-sessions, and the watcher is flagging collisions. D06B was told to wait for the other chat's handover before making changes. The diagnosis was posted to the d-board so the stuck session could use it.

- **Not a missing `arr=` parameter on the client fetch.** The client *doesn't even send* `arr=` to `/api/plates` because the server endpoint doesn't support it. This is a chicken-and-egg: the server must be fixed first, then the client call can pass the parameter.
