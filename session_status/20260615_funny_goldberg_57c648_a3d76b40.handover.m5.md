## DECISIONS + WHY

1. **Router identification**: Found gateway at `192.168.1.1`, running OpenWRT. Login credentials (`root`) were in a saved logins file at `C:/Users/maxre/Nextcloud/zSyncMain/ssh/shared_logins_frequent.txt`. This worked.

2. **Access method**: Built a small Python helper using `paramiko` at `C:/claude_base/tools/router_kidde/rcmd.py` to send commands over SSH to the router (password-based auth). This was chosen because `sshpass` wasn't available, `plink` wasn't found, and `paramiko` was confirmed present.

3. **Root cause discovered**: The router's 2.4 GHz radio (`radio1`) was **disabled entirely** (`disabled='1'` in UCI config). The SSID "Rempel" Max's phone sees is served by the **5 GHz radio only** (`radio0`). Since Kidde is 2.4 GHz-only hardware, it saw zero signal from Max's router - only neighbors' 2.4 GHz networks.

4. **Fix applied**: Rather than modifying the existing "Rempel" SSID (which would disrupt 5 GHz service and possibly touch Max's main password), a **separate temporary IoT SSID** called `KiddeSetup` was created on the 2.4 GHz radio, targeting exactly what Kidde needs:
   - `radio1` re-enabled, channel 11, 20 MHz width
   - SSID `KiddeSetup`, password `kidde12345`
   - WPA2-PSK only (no WPA3, no mixed mode)
   - No band steering (separate radio, inherently 2.4 GHz only)
   - Broadcast enabled, DHCP inherited from LAN bridge
   - No MAC filtering, no client isolation
   - Changes saved and Wi-Fi reloaded

5. **Verification**: Ran `iwinfo` on the router - `KiddeSetup` showed as live and broadcasting on the 2.4 GHz radio.

6. **Main "Rempel" network untouched**: Password and 5 GHz config were left alone. Two old, already-disabled 2.4 GHz SSIDs ("Rempel3 2.5G" and "Rempel4 2.4G Bajor") were also left alone.
