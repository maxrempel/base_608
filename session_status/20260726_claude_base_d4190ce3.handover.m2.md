## DECISIONS + WHY

### 1. Lakarian: killed runaway backup, disabled broken cron
- `lak2cent.sh` was copying 720p song-timing videos from Lak to Centauri over LAN.
- Cron ran it **every 30 min with no lock and no skip-existing logic**. Each run took longer than 30 min, so instances piled up to **327 concurrent SCP transfers**.
- Load spiked to ~19. System was barely responsive.
- **Action:** Killed all running instances + orphaned SCP children, **commented out the cron line** (kept as reference with a dated note explaining why it was disabled).
- Routine services (Cloudflare tunnel, yt-transcript, sizzler backup, MCP servers) were left untouched and confirmed healthy.
- **Decision not to re-enable:** The script has a real bug - no lock, no incremental transfer. Needs a proper fix before turning back on.

### 2. Internet slowdown: Lak and Asto were clean, Centauri was the culprit
- Lak's backup pileup was LAN-only, no internet impact.
- Asto: only the idle dictation server, clean.
- Centauri: running Dropbox + Nextcloud (both idle), but the real bandwidth hog was a **custom Python Odysee uploader** (`odysee_upload.py`) publishing Tamza video backlog to Odysee at ~7.5 Mbps sustained upload for days.

### 3. First throttle: 4? slowdown (25% ? 6.25% of measured line)
- The uploader has a baked-in token-bucket throttle that paces uploads to a percentage of the last speedtest result.
- Was set to 25% of measured line day/night (~7.5 Mbps on ~29 Mbps line).
- **Action:** Quartered the throttle to ~6.25% ? ~2.5 Mbps. Confirmed live.
- Also discovered an **older doc** (`tools/odysee_throttle/README_tomemex.md`) describing a deprecated setup using OdyseeSync.exe + Windows QoS cap. Updated it with a dated note explaining the custom Python uploader superseded it.

### 4. Final policy: night-only, 50% during 00:30-06:30 Pacific, paused all day
- Max wanted day pause + faster upload during a narrow night window.
- **Action:** Patched `odysee_upload.py` to:
  - **Check system clock** against Pacific time.
  - **00:30-06:30:** NIGHT mode, throttle at 50% of measured line (~19.8 Mbps on the current ~39.7 Mbps measurement).
  - **Outside window:** DAY mode, fully paused (rate = 0).
  - The uploader now **stops itself at 06:30** even mid-video (resumes cleanly next night, no duplicates).
- Rescheduled the Windows task (`OdyseeUpload`) to **auto-start at 00:30 nightly**, retry hourly through 06:30, then stop.
- Updated the README again with the final policy and committed.

### Key technical decisions
- The throttle percentage is baked into the Python script itself (not an external config). Edits must be exact replacements.
- The uploader uses the existing speedtest state file from the `OdyseeThrottle` scheduled task (which still runs every 30 min to measure line speed).
- Hook false-positives forced switching from inline SSH to script-file piping on Centauri.

## GOTCHAS

1. **Centauri SSH + inline heredocs trigger Claude's hook** - always pipe PowerShell scripts via a local temp file (`scratchpad`) using `Get-Content` piped to `ssh`, never inline `$s = @'...'@`.
2. **BOM bytes break PowerShell** - any script piped to Centauri must start with a comment (`# absorb-bom`) as the first line, otherwise `Stop-ScheduledTask` etc. silently fail.
3. **`odysee_upload.py` throttle is percentage of measured line, not absolute Mbps** - the speedtest task (`OdyseeThrottle`) updates the measured rate, and the uploader reads that state file. If the line speed changes, the upload rate changes proportionally.
4. **The Lak backup cron was every-30-min with no lock** - if re-enabled without a fix, it will pile up again. The script re-copies every file from scratch each run.
5. **The old doc** (`README_tomemex.md`) described `OdyseeSync.exe` + Windows QoS - that setup is superseded. The live uploader is the custom Python script. The doc now has two dated notes flagging this.
