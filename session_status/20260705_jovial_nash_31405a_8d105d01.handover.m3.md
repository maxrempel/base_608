## DECISIONS MADE + WHY

### 1. Root cause of imager pollution: server never scoped plates
The imager grid draws from two data pipes: **shots** (`/api/jobs`) and **reference plates** (`/api/plates`). Shots were already scene-scoped by the server. Plates were **not** - the server shipped all 1,184 plates from every scene ever. The client-side filter in `runner_core.js` would hide wrong-scene plates, but it could blink during text-search-clearing or page load, flashing 1,159 pollutant plates for a moment before D04B's 2-second re-assert healed it. That blink-and-heal is why the other stuck chat couldn't see the bug - every time they looked, it had already cleaned itself.

### 2. Fix: scope plates on the server (not just heal the blink client-side)
Making `/api/plates` honor the `?arr=` query param means the browser never receives wrong-scene plates. The flash becomes structurally impossible - no reliance on a browser catching itself every 2 seconds.

### 3. Targeted restart only
Only killed and restarted the pythonw process on port 8779 (combo_gui.py). Left the render worker, Chrome, and slideshow untouched so other D-sessions' in-flight jobs weren't disrupted.

### 4. Storyboard "leakage" - ruled out filter bug, shifted to data corruption
Investigated thoroughly: all 119 pile tiles are genuinely Scene 11. The "675 images" counter is a global `ST.images.length` - misleading but not a leak. Max then clarified the ancient images are *newly appearing* in the pile, meaning they were **reassigned to Scene 11 arrangements today** by some session. This is now a data-integrity investigation, not a code filter bug.

## GOTCHAS + DEAD ENDS RULED OUT

- **The imager filter "blink" was already being healed** by D04B's 2-second re-assert, making the bug invisible to anyone watching live. Only a fresh-eye trace of the data flow caught it.
- **The "675 images" storyboard counter is NOT scene-scoped** - it's `ST.images.length` (line 441 of storyboard_editor_v2.html), a global count of all loaded images across every scene. This is misleading UX but not a leakage bug.
- **The `imgInScene` function's inclusive fallback** (line ~1006) returns `true` for images with NULL `arrangement_id` AND empty or non-"sc" `scene_id`. This looked like a leak vector but was **ruled out** - live data showed 0 such images in the actual pile.
- **The storyboard pile is built from a curated `bin_order`** stored in D1. When `bin_order` is empty, the client falls back to filtering `ST.images` by arrangement. The fallback logic is correct for Scene 11 (computes 142 items, all legitimate).
- **Imager (8779) and storyboard (8790) are separate server processes.** Fixes to one don't affect the other.
- **D24 and D30 were actively editing storyboard files** at the time of investigation - coordinate on the board before touching storyboard code.
- **MCP Playwright browser tools require explicit `browser_close`** to release the lock for other sessions.
- **The moma repo was clean** on master (only other sessions' scratch scripts) at time of commit.
