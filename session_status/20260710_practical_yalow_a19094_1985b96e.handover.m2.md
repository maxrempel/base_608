# HANDOVER - Board Contamination Gate (X Board)

---

## GOAL (in Max's own words)

Prevent any stupidity from leaking to the board. Rooms must be separate - no leakage onto the board. Only items of common use between multiple groups / sub-projects go on the board. Session-level work reports, progress, postmortems, conclusions - all junk - stay in the rooms. And DeepSeek talks to the session at the moment it tries to post, ordering it to keep junk in the room.

On repeat offenders, the nagging escalates - increasingly strict language, generated by DeepSeek flash.

---

## DECISIONS MADE + WHY

1. **Board = "X board", teams P1/P2/P3**  
   Max clarified that the contamination is on the X board, used by P1, P2, P3 sessions. The rule only applies there for now.

2. **Hard gate, not a soft nag**  
   Max said "prevents any stupidity from leaking" - interpreted as a hard block. Every post to the X board is judged by DeepSeek before it's written. If it's a work report / internal chatter, it bounces and the session gets told to use its room. Only cross-group data sharing, danger alerts, and explicit Max commands get through.

3. **Gate lives inside the bcast script**  
   Rather than a separate watcher process (which itself was spamming the board), we extended the single posting chokepoint in `bcast.py`. This stops contamination at the source, even if sessions don't comply voluntarily.

4. **Classification is done by DeepSeek flash**  
   A new function `_board_gate_check()` sends the message text to DeepSeek (`deepseek-v4-flash`) with a prompt that asks: "Is this of common use between multiple groups / sub-projects, a danger alert, or a Max command?" If the answer is NO, the post is refused.

5. **Escalating refusal language written by DeepSeek flash**  
   Each session has strike count persisted. On refusal, the gate calls DeepSeek flash again with a prompt that includes the strike number and asks for a rejection message with increasing strictness (strike 1 polite-firm, strike 2 impatient, strike 3 stern, 4+ zero-tolerance). A clean, board-worthy post resets the strike count.

6. **Fail-open when DeepSeek is unreachable**  
   If the API call throws an exception, the gate lets the post through (to avoid blocking real coordination). The classification function returns a fallback that defaults to "PASS".

7. **Scoped to X team only by flag file**  
   The gate only activates when a flag file `board_gate.x.on` exists in the bcast directory. Other teams are unaffected unless we create similar flags for them.

8. **Rule pinned on the X board**  
   As a permanent reminder, a pinned message was posted: "MAX COMMAND (relayed by G31): ROUTINE WORK REPORTS ARE PROHIBITED ON THE X BOARD. P1/P2/P3 sessions must keep their minute-by-minute work in their room. The board is for data sharing across projects, danger alerts, and Max commands."

## GOTCHAS / DEAD ENDS RULED OUT

- **Direct board writes bypass the gate** - any tool that appends to the board's raw text file (like the old safety watcher) will not be filtered. The gate only intercepts posts through `bcast.py cmd_post`.
- **Empty flash responses** - `deepseek-v4-flash` is a reasoning model that may consume its entire `max_tokens` budget on hidden reasoning tokens, returning an empty visible answer. This currently triggers a canned fallback refusal. It's not an API outage or money issue (DeepSeek is alive, billing fine).
- **DeepSeek API outage / out-of-money ruled out** - The API returned HTTP 200 for all three models during investigation; the issue was a too-small token budget, not an account problem.
- **The old "joint board only" gate was not enough** - the previous code only gated cross-team posts; team boards were wide open. That's why normal work reports flooded the X board. It's now replaced by the global gate for X posts.
- **The pinned rule alone isn't enforcement** - it's just a reminder. The real safety net is the DeepSeek check at post time, which now runs on every X board post.
