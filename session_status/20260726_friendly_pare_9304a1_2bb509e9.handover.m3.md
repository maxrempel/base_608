## WHAT THE REAL PROBLEM WAS (Three Layers)

Two prior sessions failed because they ONLY tightened numeric scene scoping. The real root cause was deeper.

**Layer 1 - Database:** Five named scenes (essay_nonhier, media_kit, nadali, Tape 1, lesson1) all shared `scenes.rank = 0`. Movie scenes had unique ranks (9, 10, 11, 15, 200, 999). Rank 0 was also the sentinel for the "All" pseudo-selection in app_state.py line 33.

**Layer 2 - Client (storyboard_editor_v2.html):** The `arrangementchanged` event listener had this line inside it:
`const newScene = d.scene_rank ? +d.scene_rank : ST.sceneRank;`
Since Lesson 1's scene_rank was 0, and 0 is falsy in JavaScript, this silently reverted to whatever `ST.sceneRank` was before (default: 10). So every fetch used `?scene=10`, showing scene 10 content regardless of what was picked. This is exactly the symptom Max reported.

**Layer 3 - Server (slideshow_server_v01.py):** `_scene_arg` at line ~644 had a second silent fallback: `s = qs.get('scene', str(DEFAULT_SCENE))` with `DEFAULT_SCENE = 10`. If a bad scene value was passed, it quietly served scene 10 instead of failing.

**Second Bug (post-picker-fix):** After the picker fix made Lesson 1 actually switch, the left column (spine/spots/lines) was completely blank. Turns out Lesson 1 was built by a different session (K1) as a "named project": 38 reels under arrangement 42, full libretto baked into those reels, but deliberately with ZERO rows in the `script_lines` database table. The storyboard server only knew how to build a spine from script_lines. With zero rows, the left column rendered nothing. The user's "flashes then disappears" was because the pile drew (701 images from the images endpoint) but the spine/spot area appended zero DOM elements.
