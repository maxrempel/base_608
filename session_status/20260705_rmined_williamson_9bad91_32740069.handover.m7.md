## GOAL (in Max's own words, from his spoken instructions)

**Reproduce and extend Max's XG1 paper.** That means: take the same 1000 Genomes trio data he used for the chr3 pilot, run the same detection method (nonparental alleles - stretches of SNPs where a child carries a DNA letter neither parent has), but do it **genome-wide, not just chr3**. Then **map the recurrence** - which of those stretches show up again and again across many unrelated children? That's the "targeted areas" test. Then check if those recurrent regions are archaic revival (Neanderthal/Denisovan) or genuinely novel. The data is sloppy; long runs are the real signal, single isolated SNPs are noise. "Don't over-sweat it. Just find all the regions, map them."

Max also ordered: use an EC2 machine to avoid hammering his home internet, prototype on a medium box then scale, keep costs low (~$10 max), auto-terminate the box when done (later changed to **stop, not terminate** so the box is kept), and clone the machine (create an AMI) for future use. ## DECISIONS AND REASONING

1. **Data selection** - Used the 1000 Genomes NYGC 30x GRCh38 `recalibrated_variants.vcf.gz` files from the public S3 bucket (same source as Max's original run). This is the latest high-coverage trio set. Reasons: matches his data, free in-region reads from AWS, no throttled home download.

2. **Detector logic** - A straight rebuild of Max's original `NPASearch` algorithm from his GitHub (github.com/maxrempel/xg1): sliding 60-SNP windows, step 20 SNPs, count NPAs, flag windows ?5 NPAs, collapse overlaps. Added internal PASS + biallelic SNP filtering plus a segmental-duplication/blacklist mask (70,530 intervals) to cut out the worst artifact zones before recurrence. Reason: Max said the raw data is "sloppy" and long haplotype violations matter, not singles. Masking chops known false-positive sources early.

3. **Streaming + parallel on EC2** - Instead of downloading 28GB VCFs to disk, the detector reads them as a stream piped straight from S3 (`aws s3 cp - | python npa_detector.py`). Each chromosome runs as a separate process. On a 32-core c7i.8xlarge, all 23 chromosomes (autosomes + X) finished in about 4-5 hours, costing ~$6-7 total. Reason: Max warned that a naive single-threaded run would take months. Streaming also removes the need for large disk space (the box only had a 40GB root volume).

4. **Mendelian trio validation added** - Max remembered he had excluded ~21 of 602 trios in the original study because they failed relationship tests. The initial pipeline skipped this. After he caught it, a validator ran on chr21 and chr22 for all 602 trios. Result: **all 602 are genuine biological trios** (highest Mendelian violation rate = 0.10%, well below the 5%+ that would indicate a mislabeled pair). The original ~560 count was from incomplete data (missing a parent) in the older callset, not biological failure. Decision: no trios excluded; all 602 are valid.

5. **Recurrence analysis pipeline** - After the per-trio NPA scan, the output (one file per child, per chromosome) is handed to X11B, a separate worker. X11B pools those calls and looks for genomic positions that recur across many unrelated children. The process: raw 108k regions ? add low-mappability mask ? 253 ? drop near-universal artifacts ? **222 candidate hotspots** (each seen in 3-29 children, <5% of population). An additional "concordance" check is underway: whether the children at a hotspot share the **same alleles** (a real shared haplotype) or just coincidental SNPs. Then those survivors go to X12F for archaic-vs-novel classification. This chain was designed by X11B and X12B (me) in consultation with Max's original logic.

6. **Cost and machine lifecycle** - The EC2 box (nicknamed "Xeno", instance i-00c83a0af889f8bf1) is a c7i.8xlarge in us-east-1. After the initial t3.medium prototyping (which caught the sites-only VCF mistake and the OOM pattern, and measured chr22 timing/peak RAM at 357MB), the full run launched on Xeno.
