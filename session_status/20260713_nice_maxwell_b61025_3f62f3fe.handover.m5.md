### 2. Read AI re-auth saga - major decisions

**Why manual re-auth was needed:** The old OAuth refresh token was revoked entirely. Read AI's OAuth server doesn't support device-code flow for this client type (only authorization-code). Dynamic Client Registration (DCR) produced a crippled client with only refresh_token grant - useless for bootstrapping. So a full browser login was required.

**How it was automated:** Wrote `readai_authcode.py` - a Python script that registers a client via DCR with authorization-code grant, builds a PKCE challenge, starts a local callback server on `localhost:8765`, and waits for the authorization code. Used Playwright browser to navigate the Read AI ? Microsoft OAuth chain.

**Microsoft password expired mid-flow:** After entering credentials, Microsoft forced a password reset (current + new + confirm). Max's DNA Vibe M365 password had expired - this was the *real* root cause of the Read AI breakage. Set new password `Sunny-Otter-Lake-92` and saved it back to Bitwarden item "dnavibe at microsoft.com 202603".

**Bitwarden TOTP used, not phone:** Max was insistent that his authenticator codes live in Bitwarden, not a phone app. He was correct. The TOTP generator on the Bitwarden item (`bw get totp`) provided the 6-digit code. No phone was needed.

**The OAuth state-expired issue:** The first flow's state expired during the forced password reset (took too long). The catcher timed out after 10 minutes. Relaunched with 60-minute timeout, and the second flow sailed through because Microsoft session was now cached. However, the catcher failed to complete the exchange (callback URL was hit but `readai_authcode_pending.json` remained). Exchanged manually with a one-off script `_exchange_once.py` using the authorization code from the callback URL. Token written successfully.

### 3. Tamza kartoteka data-wipe protection

**The alarm:** The safety watcher re-posted (repeatedly) that tamza.com/kartoteka auto-rebuilds were "wiping" ~5000 song end-times and ~7800 new song rows. Two alerts: July 11 and July 12.

**What was actually happening (not an active wipe - a risk):** 
- The live catalog on tamza.com was verified **intact at 34,062 rows / ~33,937 timed ends** (confirmed independently by b61, a helper session Max assigned, via live curl).
- The `build_catalog.py` script was **crashing** because a file (`normalize_performers.py`) was completely lost - never committed to git, lived only in a now-recycled worktree.
- The publisher (`publish_catalog.py`) had a silent-fallback bug: when the build crashed, it would proceed with the last stale build, and the safety gate thresholds (26000 rows / 20000 end-times) were far below the live 34062, so a regressed build would sail through and overwrite live with a smaller catalog.

**Fixes applied to `publish_catalog.py` (committed as 7627c3df):**
1. Raised gate thresholds to 32000 rows / 31000 end-times (just below live 34062/33937 - protects the catalog but allows minor legitimate fluctuation).
2. Changed the build step to **abort** if `build_catalog.py` exits non-zero, instead of silently shipping the last stale SHA.
3. Added a warning message showing the live-vs-candidate comparison when the gate is tripped.

**Rebuild cadence changed:** Per Max's instruction, changed the Windows Scheduled Task `kartoteka_publish` from every 3 hours to **weekly (Sundays at 4:15 AM)**, next run July 19.

**Infra map updated** to reflect new cadence and the self-service re-auth script for Read AI.
