## DECISIONS + WHY

**Chose self-build over ready-made tools** because every existing option (Zemail, ragmail, semantic-mail, Context Link, Shortwave, Missive) either (a) ran laptop-only (defeating the "anywhere" requirement), (b) was unproven/solo-built with no reviews, or (c) cost enterprise money. Self-build was the only path that hit all requirements.

**Chose semantic-mail (yahorbarkouski) as the ingestion base** after ruling out ragmail (Rust/`just` dependency, 25-hour Windows ingest claim) and Zemail (unproven, closed API). semantic-mail is pure Python, light, already handles Gmail OAuth + embeddings.

**Built v02 - Cloudflare Vectorize + teal16 - NOT local ChromaDB.** The initial v01 (local ChromaDB on Pine) would have stored vectors on the same 13GB-free C: drive. When we discovered 505k emails and the per-month archive could be dozens of GB, the design was rewritten so:
- **Vectors** live in **Cloudflare Vectorize** (index `max-emails`, 1536-dim, next to Memex's own `claude-memory` and `babel` indexes). Searchable from anywhere.
- **Full archive** (.eml + every attachment) lives on **teal16** (Centauri D:, 12.9TB free).
- **Pine** (now **asto**) only stages one month at a time, ships to teal16, then deletes the stage.
- **Rebuild-source backup** (JSONL of vectors per month) also on teal16 (`D:\mail_archive\_vectors\`).

**Migrated runtime from Pine (laptop) to asto (always-on Debian).** Pine sleeps, pausing the multi-day job. asto never sleeps, fits the guest rule (stages-then-deletes, no permanent storage), and has 985GB free. The pipeline resumed from exactly where Pine left off (34 months done, continued from 2023-08).

**Used existing Google OAuth client** (`stalwart-coast-240620` project, desktop app type) rather than creating new credentials. Read-only Gmail scope - account-safe.

**Used OpenAI embeddings** (`text-embedding-3-small`) because privacy isn't a concern per Max's explicit call ("fuck privacy, only care that Google doesn't close my account"), and they're fast/cheap (~a few $ for the whole mailbox).

**Month-by-month, most-recent-first, resumable** - each month commits durably before the next starts; a crash or reboot loses nothing; recent mail becomes searchable fastest.

**PDFs and DOCX indexed, images saved but not embedded** - exactly per Max's spec ("PDFs, docs. Images can be unindexed but saved").

## GOTCHAS & DEAD ENDS

1. **Do NOT run the body-only ChromaDB index again.** It was the v01 approach that would fill Pine's 13GB C: drive and had no attachment indexing. Stopped and superseded.

2. **Google Takeout was discussed but never triggered.** The pipeline uses the Gmail API (OAuth), not Takeout. If a bulk re-ingest is ever needed, Takeout is the official "everything at once" export - but it wasn't used here.

3. **Context Link** was over-sold by Claude and then retracted - it's a solo dev's new tool for sharing docs, not a proven 500k-email semantic search product. Dead end.

4. **Zemail** sends all email text through ZeroEntropy's cloud API and only works as a local Claude Code plugin - doesn't reach phone. Dead end per Max's requirements.

5. **ragmail** (by 0xfe) looked promising (same use case, 22-year inbox) but requires Rust + `just` + estimated 25-hour local ingest on Windows. Not tried.

6. **The openai_embedder.py long-email bug:** A single email >8192 tokens killed the ENTIRE embedding batch silently. Patched to truncate per-email using tiktoken. If re-cloning semantic-mail, this patch must be reapplied (it's in tools but not upstream).

7. **The `_vectors` clobber bug:** scp treated `D:\mail_archive\_vectors` as a filename (not a dir) because the remote dir didn't exist pre-creation. Each month overwrote the last. Fixed by mkdir on teal16 + driver hardening. Verified working.

8. **Disk guard:** the driver checks free space before each month. On Pine it guards `C:\`; on asto it guards the stage dir's mount point. If a stage exceeds the guard threshold, the driver aborts that month safely.

9. **asto's SSH key** for teal16 needs the `sol_key` (scp'd during migration). If teal16 moves fail on asto, verify `~/.ssh/sol_key` exists in the distrobox container with perms 600.

10. **bcast / worklog `cd` bug:** Both the branch bulletin board and worklog key their identity/state by `$CWD`. If you `cd` mid-session before calling them, you lose your identity (E10) or write to the wrong file. C6 owns this bug; E10 reported it. In the meantime: always `cd` back to the worktree before posting.
