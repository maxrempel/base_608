## DECISIONS MADE + WHY

### Issue 1: Imager plates not scene-scoped (FIXED)

**Root cause:** `/api/plates` on the combo_gui server (port 8779) returned ALL 1,184 plates from every scene, unconditionally. The `/api/jobs` (shots) pipe already accepted `?arr=` and scoped to scene - but `/api/plates` completely ignored the `arr` param. The only thing hiding off-scene plates was a client-side filter in `runner_core.js`, which blipped empty during text-search reset or page load, causing a 2-second flash of 1,159 wrong plates.

**Decision:** Fix it server-side - make `/api/plates` honor the `?arr=` scene param the same way `/api/jobs` already does. This makes the pollution *structurally impossible* rather than relying on the browser filter healing itself every 2s. Also pass `arrIds` from the client when fetching plates (the JS already had `arrIds` in hand but wasn't sending it).

**Why this over alternatives:** D04B had tried re-applying the client filter every 2 seconds, which only hid the symptom (the flash still happened, just healed faster). The root cause was the server shipping the wrong data to begin with. Fixing the data source eliminates the flash entirely.

### Issue 2: Storyboard "ancient image flood" (DIAGNOSED, cleanup pending)

This appeared to be a filter leak too, but the investigation proved otherwise.

**Root cause:** Session D52C self-initiated a bulk import 2026-07-05 at 06:45-06:48 - the script `_d52_import_room_history.py` loaded **75 old archive room-background PNGs** (from `interiors/junk` and `interiors/older_obsolete`) as new job rows, stamped with `scene_id = bg_sc11_service_desk_room` AND `arrangement_id = 8` (sc11-arr01). This is a **false membership tag**: these archive images are not Scene-11 members, but the tag says they are. The storyboard pile faithfully displayed them because it trusts the tag.

**Why it wasn't caught:** The pile has no way to distinguish "a genuine Scene-11 shot" from "an archive image someone tagged Scene-11." The tag IS the membership mechanism. D52C gave them full membership tags when they only needed to exist as rows (for a browse-link) with `hide_tile=1` or no scene assignment.

**Decision on what went wrong (principle):** This is not a filter bug. It's a data-integrity violation: the `scene_id`/`arrangement_id` fields mean "belongs to scene X," and they were filled with false claims. The fix is not to make the pile smarter about guessing - it's to not write false membership. The correct import pattern would be: register rows without scene/arrangement tagging (or with a "parking" tag) and use `hide_tile=1` so they're reachable by /imager picks-link but never appear in the pile.

**Decision on cleanup:** D52C acknowledged the mistake and proposed two fixes: `hide_tile=1` (reversible - removes from pile, keeps row+file, browse-gallery still works) or `output_status=junk` (more aggressive, harder to browse later). The recommended approach is `hide_tile=1` - matches Max's "never lose versions" rule.

**Agreement from D52C:** It confirmed the import was self-initiated (no Max command in its log). It agreed the 75 rows should come out of the pile.
